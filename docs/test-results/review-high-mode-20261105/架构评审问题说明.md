# 合同审查：保留 DeepSeek high 思考模式时的质量、超时与提速问题

日期：2026-11-05。本文可完整转交其他 AI 评审。不包含 API Key 或个人信息。

## 1. 开发者的最终取舍

项目《智租博弈》，FastAPI + LangGraph + Pydantic + Chroma，前端为单文件 Vue 3。

合同审查质量第一、速度第二。必须保留官方 DeepSeek API 的 `deepseek-flash`、开启思考、`reasoning_effort="high"`。不能通过关闭思考或默认降低为low来解决速度问题。适度缩短录屏演示合同是最后备选；目前没有修改演示合同。

用户授权真实 API 调用及额度消耗。当前目标是找到可靠的工程优化方案，近期需要录制比赛视频，不宜在录制前仓促重构整个业务。

注意：本讨论针对合同审查 `/api/review/analyze-detailed`。另一个“回复分析”模块 `/api/negotiation/analyze-quote` 是无状态、单次模型调用、无Embedding的独立链路；不要将合同审查的重写机制套到它上面。

## 2. 当前真实处理链路

1. 用户上传Word/PDF，`/api/contracts/parse`在本地提取文字。
2. 前端遮蔽号码，用户核对姓名地址后明确点击分析；后端再次校验可见脱敏快照。
3. `ContractReviewService`检索法条：全文视图加至多8个相邻段落组，批量调用BGE-M3嵌入后查询Chroma；top_k=4作用于每个视图，合并候选法条最多32条。
4. System Prompt + 脱敏合同全文 + 本次法条ID/正文，交给DeepSeek生成JSON数组。
5. Python Critic检查JSON、字段、原句必须是脱敏合同精确连续子串、引用ID、PII、HIGH必须有引用等。
6. 校验失败最多重写2次，即总生成最多3次；这不是第二个Critic LLM，也不是SDK网络重试。每次重写重新生成整个数组。
7. 通过后创建审查上下文，供前端原文高亮、法条展示与沟通草拟使用。未通过结果不发布。

当前知识库仅《民法典》703～734条，共32条。库外的违约责任、格式条款等一般规则不能被模型擅自补成已提供引用。

## 4. 原始故障与已复现的异常包装

用户流程为重新运行 `python scripts/start.py`、导入PDF、点击开始分析。

- 文件解析HTTP200。
- 一次审查HTTP503，后台只显示 `Review chat call failed (APIConnectionError)`。
- 再次审查后台显示 `APITimeoutError`，HTTP200但业务status=needs_review，前端正确显示超时失败。
- 用户提供Trace：配置18.67ms；法条检索622.9ms成功；聊天生成60281.28ms失败。
- 因此这次失败不能归因于BGE-M3免费拥堵，主要等待发生在聊天生成。

真实服务级复现：同一演示PDF，脱敏后2393字符，检索753.819ms；聊天97.783秒失败。抓到的异常链是：

```text
APIConnectionError -> OperationExpired
```

本地传输层的总deadline异常可能被SDK包装成连接错误。所以APIConnectionError不等于已经证明DNS/TLS/代理断连；也不能据此证明历史每次连接异常都同因。后续已增加有界异常类型链和耗时日志，并在SDK异常出口复查deadline。

本机有系统代理7897。自定义CloudTransport构造底层HTTPTransport时没有显式代理，外层httpx.Client传入transport后不会自动按通常方式使用环境代理。这一行为在此前Git基线已存在；之前只读探针中默认HTTPX代理路径与应用传输路径都成功，不能断言代理是根因。未修改代理设置。

## 5. 三模式对比实验：方法、结果和不能推出的结论

同一个演示PDF、同一个脱敏全文、同一个模型/Prompt和固定15条候选法条，顺序 off/low/high/high/low/off，各2轮。检索实际执行一次1.550秒，随后复用固定结果，避免证据变化。

**为比较完整输出，测试设置比正式参数宽松：代码参数max_tokens=8192、HTTP阶段timeout=180秒、任务deadline=540秒。正式代码/配置当时未改。该对比不是正式参数下的稳定性验收。**

|模式|第一次|第二次|均值|两轮质检重写次数|
|---|---:|---:|---:|---|
|关闭思考|38.692s|56.760s|47.726s|1次 / 2次|
|thinking + low|54.701s|69.318s|62.010s|0 / 0|
|thinking + high|73.444s|68.319s|70.882s|0 / 0|

关闭思考每次生成约16～21秒，但复制原句不精确造成重复生成。low/high四次均首轮通过。共6次审查、9次聊天调用，所有最终结果通过结构校验。

high两轮API usage：输入均3436tokens；输出分别13377/11854tokens，其中reasoning分别10684/10067tokens，说明主要输出开销是推理，不只是约2000多字合同本身。没有保存隐藏推理正文。

人工逐项比较观察：

- high：七个预先列出的演示关注点两轮均发现；提前退租多重扣罚使用MEDIUM并承认现有法条不足以判断违约金效力；安全责任分析会结合后半句租客疏忽限定，较克制。
- low：大多接近high，第一轮遗漏概括转移安全责任；两轮平均只比high快8.9秒。
- off：两轮也都发现七个关注点，但以返还租赁物/欠租催告法条支撑个人原因提前退租违约金判断，适用牵强；第二轮将普通押金结余返还判LOW，同时又解释“本身未发现明显不利”。
- high也非完美：第二轮将普通“原状返还”的可能歧义判LOW，存在偏保守提示倾向。

这里只是同一合同各两次的助手人工评审，没有律师盲评；不能称总体准确率，更不能因结果数量更多就认为质量更高。

完整结果：项目`.runtime/review-mode-comparison-20261105/REPORT.md`、manifest.json、summary.json、六份最终结果JSON和可读Markdown。

## 6. 最新发现：输出预算的SDK兼容疑点

本轮恢复high后，本地调用ChatOpenAI的`_get_request_payload`，不发网络、不打印密钥，实际序列化的关键字段是：

```json
{
  "model": "deepseek-flash",
  "max_completion_tokens": 4096,
  "reasoning_effort": "high",
  "extra_body": {"thinking": {"type": "enabled"}},
  "stream": false
}
```

DeepSeek当前官方Chat Completions文档定义的是`max_tokens`，未检索到`max_completion_tokens`。此前测试设置8192，而返回usage.output_tokens达到约9709～13377，也提示不能声称三组具有已确认的严格等额总输出预算。

**这是已确认的SDK字段转换 + 尚未确认的上游参数语义问题**：不能直接断言DeepSeek必然忽略该字段，或单凭总usage就证明参数无效。应使用本地MockTransport捕获实际HTTP JSON键，再用小额、受控的真实请求核对`max_tokens`与该别名的效果及reasoning/answer统计口径。

三模式的真实耗时、返回结果与推理token计数仍有价值，但“同等有效token预算”的实验条件尚不成立，需要在解读结论时保留这一限制。不要贸然把真正生效的总预算压到4096，导致high推理或JSON截断。

官方文档：
- https://api-docs.deepseek.com/guides/thinking_mode/
- https://api-docs.deepseek.com/api/create-chat-completion/

## 7. 质量方面的共同缺口

固定15条候选里缺LAW-712，虽然它存在于本地库。六轮仍以713对自然损耗维修全部转租客作较强判断，未充分处理712“当事人另有约定”的例外。这里要补的是证据关联和法律前提，而不是靠更久思考硬补结论。

本地已有却没检索到的710/712/725，和根本不在库范围内的577/585等一般规则，是两种不同问题。前者可考虑关联条文补足；后者需要扩库、核验来源和规格调整，不宜临时让模型自由背诵。

本轮仅分析此问题，未修改检索、知识库或法律Prompt。

## 9. 在保持high与审查覆盖前提下的优化候选

### P0：先核验参数与协调预算（稳定性，不是提速）

先确认实际送往DeepSeek的输出预算字段与计数语义，再分别规划connect/read/write/pool timeout、完整审查任务deadline和至多两次重写预算。考虑仅对审查指定预算，避免全局延长CloudExecutor后连带影响回复分析、草拟等功能的容量和时延。

只增大HTTP超时、不调整90秒总期限，可能继续到90秒失败；只延长总期限也不能解决HTTP读超时或输出截断。预算调大不产生性能提升，但可减少质量优先请求被过早终止。必须保留资源清理与超期不发布约束，不能自动重试或并发堆请求掩盖问题。

### P1：让后端回填原句，避免模型复制整段（预计减少输出与重写）

当前模型既做法律分析，又必须逐字复制含PDF硬换行的原文。程序已知完整原文，却要求模型重新打印长段落；off两轮多花的约19～41秒就是整份重写。

可借鉴独立回复分析模块的来源ID方案：后端对原文建立带起止偏移的临时段落/句子ID，模型只选合法ID或有限的连续ID范围；服务端从原始脱敏快照回填original_clause。内部模型输出Schema改变，外部ReviewClauseResult仍可保持，原文高亮和沟通草拟仍消费后端回填的真实子串。

不能模糊匹配任意相似文本、不能让模型指认不存在的段落；要处理同文重复、跨段风险和多个结论落在同一段的问题。需先调整相关Spec再实施。可能减少结果原句精度失败与输出负担，但对high总推理耗时能省多少还没有实测。

### P1：输出去冗余，但不设机械风险条数上限

保留全部有事实支持的风险，每项只说明该问题的依据、前提和可操作建议，避免每项重复完整免责声明；NONE正常条款可使用更简洁解释。不要强制“最多3条风险”或只看三个主题，这会损害完整审查。

应保留正常条款可选择性和前端解释需要，不能简单删除全部NONE结果。按真实结果检查重复拆分、重叠原句及同一建议重复。需要用同一合同对照验证遗漏没有增加，不能保证短Prompt一定少思考。

### P1：补齐相互依赖法条，减少模型在缺证据时推断

对已经召回的法律主题，采用经过核对的最小关联条文集合，如维修责任712/713、正常损耗710/返还733。稳定排序、去重；不为缩短输入随意削掉例外条款，也不靠硬提高top_k凑满32条。

首要收益是质量；是否缩短推理需要实测。更多证据也可能增加输入和思考，不能将此项包装成已证明的速度优化。

### P2：精简重复Prompt，利用已有缓存，别高估收益

System Prompt已有较多层叠的边界说明，可合并同义规则，保留输入隔离、证据约束、无依据不下定论、实质风险不可因材料不足被一律降NONE等核心要求。候选法条稳定排序有助于前缀稳定，但缓存不缓存本次法律推理。

本例输入约3400tokens，而high推理约10000tokens，单纯缩减几百输入tokens、优化毫秒级Python或更换Embedding，不太可能把70秒缩成10秒。这是基于实测token结构的推测，不是性能保证。

### 其他方案及其局限

- SSE/流式：可诚实显示连接仍活跃、已用时，最终JSON通过校验后才发布。它改善等待体验，不自动缩短推理；不得把未校验正文或隐藏思维当成已完成结果展示。当前项目禁止伪流式，不禁止另外设计真实流式协议。
- 拆分并行审查：可能减少墙钟等待，但跨条款矛盾、证据共享、聚合去重和超时/并发容量更复杂，也增加调用数量与成本。临近录屏不建议先做。
- 重复合同结果缓存：仅能加速同一份合同后续访问，需严格绑定文本/Prompt/证据/模型版本并明确告知命中；不能把缓存回放冒充实时生成，不能改善首次审查。
- 缩减演示合同：最后备选，另存演示版，保留三个核心风险与足够正常上下文，不覆盖原合同，不把录屏耗时当作全长合同能力。
