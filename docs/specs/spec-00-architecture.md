# Spec 00：智租博弈总体架构与核心契约

状态：Day 1 初始化，2026-10-11 经开发者授权补充 Day 5 详细审查与 Trace 契约。本文约束模块输入、输出、状态提交与验收；各功能实际完成情况见 README 与实测报告。

2026-10-15 Day 11 增补：经开发者授权，详细审查接口增加确定性输入范围护栏，并澄清材料不足与具体不利约定的风险判定口径；不改变旧接口兼容要求。此增补是契约，不代表已完成真实模型评估。

## 1. 系统定位与场景边界

智租博弈面向青年租房中的押金扣留、维修责任、提前退租三个高频维权场景，形成“合同风险审查 → 实景谈判演练 → 协商清单导出”的闭环。风险结论须显示原条款、解释和可追溯依据；谈判结果是模拟协商进展，不代表现实房东接受概率或法律结论。

模块名映射：合同风险审查即“契光排雷”，实景谈判演练即“沉浸道场”。

首版采用 Python 3.12、FastAPI、Pydantic、LangGraph、本地 ChromaDB、云端聊天与中文向量 API、单文件 Vue 3 网页。前后端同源运行；会话按 `session_id` 隔离，存于单进程内存，重启即清空。首版不纳入 OCR、账号、长期历史、小程序或复杂文书。

## 2. 数据与安全边界

- 浏览器先用正则遮蔽手机号、身份证号，展示可人工编辑的脱敏预览；用户确认后才上传。姓名、住址等自由文本由用户在预览中检查和删改。
- 后端在调用任何云端聊天或向量 API 前二次复查并遮蔽上述敏感信息。首版风险条款定位、高亮和返回的 `original_clause` 均以脱敏文本为坐标基准，避免与原文偏移错位。
- 权威法条库范围锁定《民法典》合同编第十四章“租赁合同”第 703～734 条，共 32 条。每条保留条号、正文、来源 URL、核对日期；入库和引用时按条号及来源核验。范围外问题应明确提示需要补充依据。
- 演练内容为 3 类核心租房演练场景（押金扣留、维修责任、提前退租）及配套的 20 个常见霸王条款参考案例，仅作场景与话术构造，不作为法律依据，不得混入权威法条库。参考案例与验证阶段的 20 例固定工程测试集（10 风险 + 4 正常 + 3 范围外 + 3 异常输入）严格区分。
- `.env` 与真实密钥不入库；日志、trace、Prompt 快照和测试结果中不记录真实个人信息或密钥。

## 3. 两条执行图与状态契约

### 3.1 合同审查图（Risk Graph）

详细审查接口在原输入字段校验、后端脱敏和现有有效长度校验后，先执行确定性输入护栏，再进入配置检查、检索法条 → 风险分析 → Critic 质检 → 输出完整 JSON。护栏位于真实聊天客户端初始化、检索和任何云调用之前；仅拦截高置信的明确非租赁文本、纯程序载荷或无可读合同内容，模糊文本、有效租赁文本及含真实租约内容的混合文本继续原流程。每条风险项至少包含：

| 字段 | 契约 |
| --- | --- |
| `clause_id` | 与脱敏合同中的条款/片段对应的稳定标识 |
| `original_clause` | 可在脱敏合同中定位的原句；无法定位时明确标记，不伪造位置 |
| `risk_level` | 风险等级，由后续模块 Spec 固定枚举与判定口径 |
| `explanation` | 面向用户的风险解释，不能超出已核验依据作确定结论 |
| `evidence_ids` | 指向权威法条库的条号/记录 ID；引用须能回查正文与来源 |
| `negotiation_tip` | 与该风险对应的具体协商建议 |

状态放在响应顶层，不要求每条风险项重复包含 `status`。详细版 `POST /api/review/analyze-detailed` 返回 `success/needs_review`；失败时结果为空、风险数为0，并返回受控原因、`errors` 和真实 Trace。风险数0在失败响应中表示没有通过质检的结果，不表示合同无风险。既有 `POST /api/review/analyze` 保留 `success/mock` 兼容格式及失败演示回退；新调用方需要分辨真实失败时使用详细版。完整字段和异常出口见 [Spec 02](spec-02-risk-review.md)。

Day 11 输入护栏拒绝时返回 HTTP 200、`needs_review`：明确非租赁为 `OUT_OF_SCOPE`，纯程序载荷或无可读合同内容为 `INVALID_CONTRACT_TEXT`。此时 `results=[]`、`total_risks=0`、`retry_count=0`，`errors` 为非空受控反馈，Trace 仅记录实际执行的 `input_guard/needs_review`；不得补造配置、检索或图节点，也不得将未检索的拒绝称为 `NO_EVIDENCE`。护栏通过时保留既有配置起始的 Trace 顺序，不额外增加通过事件。原输入字段校验与旧接口行为不变。

Day 11 语义 Prompt 口径：仅有材料不足、摘录未展示完整约定或一般性的上下文缺失，不能直接推定合同具有实质风险，可用 `NONE` 并说明需补充材料；文本中已写明的具体不利约定仍按风险内容与实际检索依据判断，不能以材料不全统一降为 `NONE`。法条引用存在不等于实质支持，仍需单列真实模型语义复核。

Critic 检查 JSON 结构、原句定位、证据可追溯性和解释是否受证据支持。返回完整 JSON 后，界面播放实际节点执行 trace，标记为“本次执行回放”；只展示真实节点状态、证据、反馈摘要与耗时，不展示模型隐藏思维。

Day 5 Trace 包含真实执行过的配置检查、检索、起草、Critic 和失败终止节点；每项含连续序号、节点、生成次数、状态、耗时、法条 ID 和受控反馈。未进入的节点不得补造，异常前已完成的记录须保留。Trace 按请求隔离、不持久化原始状态；不得包含合同文本、消息、未通过草稿、原始异常或密钥。当前 Critic 实现为确定性校验；解释是否受到法条实质支持仍需后续语义复核，不能宣称已全面实现语义质量验收。

Day 11 新增的 `input_guard` 仅在实际拒绝输入时形成一条 Trace 事件，沿用连续序号、实测非负有限耗时和受控反馈要求；不含输入原文，准备阶段的生成次数为0、法条 ID 为空。

### 3.2 实景谈判图（Negotiation Graph）

执行顺序：用户输入与租客辅导 → 模拟房东回应及候选条件提取 → 确定性规则试算分数 → 模型解释与 Critic 质检 → 校验通过后提交 `confirmed_terms` 与分数。

- `session_id` 是会话隔离键。单会话最多 5 轮；正式会话状态至少区分已确认条件、当前分数、已完成轮次及重复请求标识。不同会话不得互相读写。
- 模型可识别候选动作、模拟回应和解释；只有房东明确确认且 Critic 校验通过的条件才进入 `confirmed_terms`。租客单方诉求不是已确认条件。
- 试算在候选状态上进行。失败生成、失败质检或内部重试不得修改正式会话状态、增加轮次或累计分数；重复请求也不得重复提交。

## 4. 有界自纠错与失败出口

初次生成设 `retry_count = 0`。Critic 校验失败且 `retry_count < 2` 时，才递增计数并打回重写。最多重写 2 次，总生成最多 3 次。仍不合格时返回 `needs_review`，附可解释的失败原因并终止该次流程，绝不继续循环。风险图与谈判图均遵循该上限；谈判失败回合绝不提交正式状态或累加分数。

## 5. 确定性规则混合算分

单项进度 `p = clip((confirmed - start) / (target - start), 0, 1)`，单项 `score = round(100 * p)`。`target = start` 时不得直接除以零，需由后续规则 Spec 明确定义该项是否适用及其处理方式。

多项按适用权重归一化：`score = round(100 * Σ(wᵢ * pᵢ) / Σwᵢ)`，求和仅包含适用且权重有效的项目；无适用项时返回“不可评分”，不伪造零分。模型只解释规则结果，不生成或覆盖最终数值。相同确认状态应得到相同分数；租客单方诉求、重复引用法条、重复请求和内部重试均不触发加分。界面标注“模拟协商进展分”。

## 6. 后续验收口径

后续模块需用真实执行结果验证：32 条法条可追溯且重复入库不重复；风险 JSON、引用和脱敏定位有效；Critic 有限退出；双会话隔离；重复请求、失败回合不加分；同状态同分；三场景从审查到清单可走通。验证阶段使用 20 例固定工程测试集（10 风险 + 4 正常 + 3 范围外 + 3 异常输入），与演练参考案例分开管理；实际测试结果、Prompt 对话、trace、耗时分别留存，未运行的指标不得写成已完成。
